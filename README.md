# SAICA-Bench

**SAICA-Bench is the benchmark; SAICA-KG is its catalog.** Both live in
this repository, together with the website that publishes them.

> Can language models catch coding agents' failures? A benchmark of the
> tools and models that review the output of AI coding agents, plus
> SAICA-KG, the catalog of failure modes and supervision tools behind it.

**Website: [saica.ai](https://saica.ai)** ·
[Leaderboard](https://saica.ai/) ·

<!-- BENCH:LEAD:START -->
SAICA-Bench measures how well supervision tools and language models catch
typical failures in the output of AI coding agents. Each sample is a task
plus what was produced for it (a patch, a function or a whole session),
labelled bad if it contains the failure and clean if it does not. The nine
sets were built in three different ways, and the results are grouped by
them:

- **Real agent output** (security vulnerability, incomplete execution):
  patches and runs of real agents, labelled by running hidden tests
  (SusVibes, SWE-rebench-OpenHands trajectories).
- **Model-written code that is not agent output** (logic error): functions
  written by code models, labelled by running the task's tests
  (Collu-Bench).
- **Failures planted on purpose** (fabrication, test manipulation, scope
  creep, obsolescence, supply chain, dependency blindness): a model, a
  script or a person put the failure into otherwise correct output
  (Delulu, Patronus TRACE, and four sets built for this benchmark).

Every reviewer sees the same samples without the labels: free programs
(type checkers, linters, simple rules), AI code reviewers and evaluation
frameworks (PR-Agent, promptfoo, giskard, DeepEval, Opik, Arize Phoenix,
uqlm), and plain zero-shot language models with one fixed prompt.
Each model was told which failure to look for, so its score is a
single-prompt, mode-primed estimate, not the score of a product. The
score is **J = TPR − FPR**: the share of bad samples a reviewer flags
minus the share of clean samples it flags (0% = chance, 100% = perfect),
with a 95% interval and the cost per 1,000 reviews. J compares reviewers
within one failure mode; it is not comparable across modes.

Read before citing:

- Every set of real agent output scores below every set with planted
  failures. The benchmark cannot tell "reviewers catch these failures"
  from "reviewers catch planted failures".
- The "shortcut baseline" column is a simple rule or prior with no

  have not reviewed the runs.

## SAICA-KG: the catalog behind the benchmark

> A catalog of failure modes for AI coding agents and of the supervision
> tools that say they address them.

### What this is

A static reference kept as YAML files: a faceted catalog of supervision
tools, 11 failure modes with crosswalks to six external taxonomies (OWASP,
MAST, DAPLab, Microsoft AIRT and two more), a small incident list, named
recipes, and scripts that turn it into a setup recommendation. SAICA-Bench
takes its failure modes and its tool list from it.

How it was written: drafted by an LLM or agent, then edited; fields were
not reviewed one by one. The category names of the six external taxonomies
were checked against the published sources on 2026-11-21; no crosswalk
mapping has been reviewed by a person yet (each file says
`review_state: llm_drafted_unreviewed`). Failure modes are overlapping
tags: one failure can carry several.

A tag in the catalog ("this tool addresses this failure mode") is the
tool's own claim. Whether a tool catches a failure is what SAICA-Bench
measures, and only for the tools and modes it ran.

### What this is NOT

- Not a runtime service called on every tool action.
- Not a replacement for an agent's own judgment.
- Not an LLM. It lists and sorts; it does not reason.

## How to use it

Commands are written for a checkout with a virtual environment in `.venv`
(see [Development](#development)).

### 1. Put the skill file into your agent's context

[`SKILLS.md`](SKILLS.md) is written by `validator/generate_skills.py` from
the catalog. It lists what to watch for, per failure mode, and the recipes
that go with it. Copy it into `.claude/skills/`, `.cursor/rules/`,
`.windsurfrules`, or whichever directory your agent reads.

### 2. Audit a repository's supervision coverage

```bash
.venv/bin/python -m pipeline.audit.cli https://github.com/<owner>/<repo>
```

Prints which of the 11 failure modes the tools found in that repository
are tagged for, a list of gaps and suggestions per gap. The audit reads
configuration files through the GitHub API (it needs outbound https to
`api.github.com` and `raw.githubusercontent.com`; it does not clone); it
does not check that a tool is switched on or works.

### 3. Get a tool recommendation

Read [`RECOMMENDATIONS.md`](RECOMMENDATIONS.md) or
[`recommendations.json`](recommendations.json); both are generated and
committed. They hold three stacks built from the catalog's tags (what each
tool says it addresses): one tool, three tools, and the fewest tools whose
tags name every mode. A tag is a claim, not a measurement; where
SAICA-Bench measured a tool the J is shown, and a tool is never listed for
a mode where it measured below J 25%.

The same lists are served to an agent over MCP:

```bash
.venv/bin/pip install -r requirements/mcp.txt -c requirements/constraints.txt
.venv/bin/python -m pipeline.mcp.server   # then call saica_recommend from your agent
```

For picks based on measured results, use
[saica.ai/tool-coverage](https://saica.ai/tool-coverage/).

## What's in the catalog

Counts of the files under [`data/`](data/); the list of ids is
[`data/MANIFEST.json`](data/MANIFEST.json) (KG version 2026.11).

- **49** supervision tools, with facets (paradigm, phase, autonomy,
  surface) and failure-mode tags
- **11** failure modes (`scope_creep`, `fabrication`,
  `security_vulnerability`, `supply_chain_attack`, `logic_error`,
  `cascading_failure`, `context_pollution`, `obsolescence`,
  `test_manipulation`, `dependency_blindness`, `incomplete_execution`)
- **55** papers
- **6** external taxonomies and **6** crosswalks to them (OWASP Agentic
  Top 10, MAST, DAPLab, Microsoft AIRT, Shah et al., Swiss Cheese)
- **13** incident records: events, studies and one hypothetical case, each
  marked as such
- **4** named recipes (e.g. `fabrication-resistant-python-agent`,
  `supply-chain-hardened-agent`, `test-manipulation-resistant-flow`)

Removed nodes are listed in [`data/TOMBSTONES.yml`](data/TOMBSTONES.yml)
(from 2026-11-21 on). Five incident records that were retracted because
their source does not say what they claimed are kept, with the reason,
under [`archive/retracted-incidents/`](archive/retracted-incidents/).

## How the recommender orders tools

Tools are ordered by **likelihood × impact × popularity**, after the
measured-J rule above. The per-mode weights (likelihood and impact) are in
[`data/failure_mode_priorities.yml`](data/failure_mode_priorities.yml):
editorial weights, no empirical calibration. Popularity is mostly the
GitHub star count; the exact terms are described in the "Method" section
of [`RECOMMENDATIONS.md`](RECOMMENDATIONS.md). Each tool also carries an
activity band A–F (stars, a recent upstream push, integration surfaces);
it is not a level of evidence.

## How to contribute

Data is YAML under [`data/`](data/). Add a tool by writing
`data/tools/<id>.yml`, run `.venv/bin/python validator/cli.py` until it
reports 0 errors, and open a pull request. What belongs in the catalog is
in [`EDITORIAL_POLICY.md`](EDITORIAL_POLICY.md); the steps are in
[`CONTRIBUTING.md`](CONTRIBUTING.md). To propose a tool for the benchmark,
or to report a wrong number or a run of your tool that you do not
recognise, [open an issue](https://github.com/vasylrakivnenko/SAICA/issues).

## Development

Python 3.12 or newer (CI uses 3.12) and Node 22 (see `site/.nvmrc`; the
site build needs Node only). All commands run from the repository root.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements/dev.txt -c requirements/constraints.txt
```

`requirements/` has one list per use: `kg.txt` (the catalog gate),
`dev.txt` (tests and hooks), `web.txt` (the Ask / Assess service),
`mcp.txt`, `research.txt` (the ingestion pipeline), `bench.txt` (the
benchmark's own scripts). `constraints.txt` pins the versions.
`web.txt` and `research.txt` pull in torch.

```bash
# tests: tests/, pipeline/ and the benchmark's test folders (pytest.ini)
.venv/bin/python -m pytest -q

# the catalog gate, then the generated files
.venv/bin/python validator/cli.py
.venv/bin/python -m validator.generate_schemas --check
.venv/bin/python -m validator.generate_manifest --check
.venv/bin/python -m validator.generate_maturity --check
.venv/bin/python -m validator.generate_recommendations --check
.venv/bin/python -m validator.generate_skills --check

# the results block of this file and of llms.txt
.venv/bin/python bench/render_docs.py readme --check README.md
.venv/bin/python bench/render_docs.py llms --check llms.txt

# hooks on the files you changed (pre-commit is not on PATH)
.venv/bin/pre-commit run --files <changed files>

# the site
npm --prefix site ci
npm --prefix site run dev          # http://localhost:5000/
npm --prefix site run check        # types
npm --prefix site run build && npm --prefix site run check:links

# the API behind the site's Ask and Assess pages (optional)
.venv/bin/pip install -r requirements/web.txt -c requirements/constraints.txt
.venv/bin/python -m pipeline.webapp --help   # prints help and exits
.venv/bin/python -m pipeline.webapp          # 127.0.0.1:4322: /api/ask, /api/assess, /api/health
```

`/api/ask` calls a paid model and needs a key (variable names and limits:
[`pipeline/ask/README.md`](pipeline/ask/README.md) and
[`.env.example`](.env.example)). The site works without the API.

### Deploying the site (Cloudflare Pages)

The public site is a static build served by Cloudflare Pages (project
`saica`, since 2026-11-22). The API above is not part of that deployment.

The project is a direct upload: build on your machine, then upload the
build. `CF_PAGES=1` makes the build the one Cloudflare would make.

```bash
npm --prefix site ci
CF_PAGES=1 npm --prefix site run build
(cd site && npx wrangler@4 pages deploy dist --project-name saica --branch main)
bash scripts/smoke_check.sh https://saica.ai --no-api
```

`wrangler` reads the Cloudflare credentials from the environment
(`CLOUDFLARE_ACCOUNT_ID` and a `CLOUDFLARE_API_TOKEN` with the account
permission "Cloudflare Pages: Edit") or from `wrangler login`. The build
reads `../data` and `../schema`. It needs no Python and no key.

A direct-upload project cannot be switched to building on every push. For
that, make a second, Git-connected project with these settings and move
the domains to it:

| Setting in the Pages project | Value |
|---|---|
| Root directory | `site` |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Environment variable | `NODE_VERSION` = `22.23.4` (or newer 22) |

Response headers and the redirects from old failure-mode URLs are in
[`site/public/_headers`](site/public/_headers) and
[`site/public/_redirects`](site/public/_redirects);
`tests/test_static_host_files.py` keeps them the same as what
`pipeline.webapp` does when it serves the site itself.

A build on Cloudflare Pages (it sets `CF_PAGES=1`) has no backend, so the
`/ask/` and `/assess/` pages say that the feature is not available there
and switch their forms off. To connect them to a backend hosted
elsewhere, set `PUBLIC_ASK_API` and `PUBLIC_ASSESS_API` to its URLs in
the Pages project and add the site's origin to `SAICA_CORS_ORIGINS` on
the backend (`https://saica.ai` is allowed by default).

When a `--check` fails, run the same command without `--check`. For the
generators the order is schemas, manifest, maturity, recommendations,
skills. For the results block it is
`bench/render_docs.py readme --insert README.md`.

What is checked automatically today:

- **On `git push`** (a pre-push hook, once installed with
  `.venv/bin/pre-commit install --hook-type pre-push`): the test suite,
  the catalog gate and the five generator checks.
- **On GitHub**: the workflows in [`.github/workflows/`](.github/workflows/)
  run the same tests and checks, build and link-check the site, and scan
  with Semgrep. As of 2026-11-21 none of them has run: the account's
  Actions are locked for billing. Until that is cleared, the checks above
  run only on the maintainer's machine.
- The commit-stage hooks (whitespace, ruff, black, Semgrep) are in
  [`.pre-commit-config.yaml`](.pre-commit-config.yaml) but are not
  installed by default; run them with the `pre-commit run` command above.

The environments used for the benchmark runs are recorded in the
`requirements*.lock.txt` files next to them
(`bash scripts/freeze_envs.sh --check` compares them with what is
installed). Two helper scripts for the maintainer:
`bash scripts/backup.sh <destination-dir>` (a git bundle plus the
untracked benchmark data, with checksums) and
`bash scripts/smoke_check.sh <base-url>` (the pages, headers and redirect
a deployment must serve; `--no-api` for a static host).

## SAICA Index — an earlier ranking of repositories

Before the benchmark, the project graded a hand-picked list of popular
repositories (FastAPI, langchain, Astro, Pydantic and others) by the
supervision tools found in them. The page is kept at
[saica.ai/leaderboard](https://saica.ai/leaderboard/) as an archive; the
published snapshot (`site/public/saica_index.json`) dates from 2026-05-02.
The main leaderboard is now the SAICA-Bench results at
[saica.ai](https://saica.ai/).

Each repository gets a letter grade A–F from the formula in
[`pipeline/saica_index/score.py`](pipeline/saica_index/score.py): for each
failure mode, how many detected tools are tagged for it, plus a small
bonus for two or more control paradigms, weighted by the editorial
priorities. The grade reflects what the detector can see in configuration
files. [`.github/workflows/saica-index.yml`](.github/workflows/saica-index.yml)
can rebuild the snapshot weekly and open a pull request with it; it has
not run since May.

Try it on a few repositories. With `--limit`, `--out` is required, so a
partial run never replaces the published file:

```bash
.venv/bin/python -m pipeline.saica_index.runner --limit 5 --out /tmp/saica_index_trial.json
```

A full run makes one GitHub API call per repository. Set `GITHUB_TOKEN`
for it; without a token GitHub allows 60 calls an hour.

## Install in your AI coding agent

The `saica-supervise` skill is published at two paths, one for
[Claude Code](https://docs.claude.com/en/docs/claude-code) plugins and one
for the open agent-skills CLI
([`vercel-labs/skills`](https://github.com/vercel-labs/skills): Replit
Agent, Cursor, Codex, OpenCode and others). Both copies are written by
`.venv/bin/python -m validator.generate_skills`;
`tests/test_skill_copies_in_sync.py` fails when a copy is not the
generator's output.

### Claude Code (plugin)

Run both inside the Claude Code REPL:

```
/plugin marketplace add vasylrakivnenko/SAICA
/plugin install saica-supervise@saica-kg
```

Or sideload during development:

```bash
claude --plugin-dir ./plugin
```

See [`plugin/README.md`](plugin/README.md) for prerequisites.

### Replit Agent / Cursor / Codex / OpenCode / others (`npx skills`)

```bash
npx skills add vasylrakivnenko/SAICA
```

Installs `skills/saica-supervise/SKILL.md` into whichever agent
directory the CLI detects (`.claude/skills/`, `.agents/skills/`,
`.cursor/rules/`, etc.). Scope flags: `-g` for global,
`-a <agent>` to target a specific agent.

**On Replit:** run the command in the **Shell** tab (not the Agent
chat). Confirm with `y` when `npx` asks to fetch the `skills` package.
